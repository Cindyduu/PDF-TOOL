### 缺陷 1：Windows 共享冲突是双向的
`app/core/atomic.py` 只给写方 `replace_with_retry` 加了退避，读方 `read_json` 裸 `open` 无重试。worker 写 `job.json` 的那一瞬间，HTTP 线程轮询读同一文件 → `PermissionError [Errno 13]` → 500 → 前端停在「校验完成」，`#start-process` 永不出现（单跑该 e2e 用例能过，全量跑挂——纯时序窗口）。
修法：抽 `_retry_denied(action)` 让两侧共用同一套退避（15 次 / 10ms 起指数 / 单次上限 100ms / 最坏约 1.2s）；常量 `_REPLACE_*` 改名 `_DENIED_*`（语义已扩到读写两侧）。
**刻意保留一条边界**：重试用尽仍抛异常，不返回 `default`——否则 `_read_job(default=None)` 会把「读不到」伪装成「任务不存在」，用 404 掩盖杀毒锁文件/ACL 问题。

### 缺陷 2：`capture_output=True` 在 Windows 上会永久阻塞
管道写端可继承；全量跑时前面 live server / playwright 的残留子进程继承了句柄，被测进程退出后写端仍有人持有，EOF 永不到来，`communicate()` 永久阻塞。faulthandler 栈指向 `test_static_v4_ui.py:340 run_notice` → `:393`，而那个 node 子进程实测 0.28 秒就跑完。
修法：stdout/stderr **落文件**再读回 + `timeout=120`（`run_notice` 与新增的 `run_cli()`）。写文件没有 EOF 依赖。**验收断言一条没动**。
